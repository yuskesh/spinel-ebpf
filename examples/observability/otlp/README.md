# spinel-ebpf OTLP export

Material for shipping the telemetry spinel-ebpf collects to an OpenTelemetry
Collector as **OTLP/HTTP+protobuf**. The encoder is nanopb
(`src/runtime/otlp/`); the transport is an HTTP/1.1 client written directly on
POSIX sockets (`src/runtime/otlp/otlp_http.{c,h}`).

- Schema of record: `deps/opentelemetry-proto` (v1.10.0)
- C encoder: `src/runtime/otlp/pb/**` (nanopb-generated, regenerated by
  `scripts/regen-otlp-pb.sh`)

## Checking the transport

### (a) Without a real Collector -- verify against the mock receiver (default)

```sh
sh tests/runtime/run_otlp_send.sh
```

`tests/runtime/mock_otlp_receiver.py` accepts `POST /v1/metrics`, restores the
body with `protoc --decode` and asserts on it. This runs entirely on the host.

### (b) Sending to a real Collector

1. Start a Collector (docker example):
   ```sh
   docker run --rm -p 4318:4318 -p 4317:4317 \
     -v "$PWD/examples/observability/otlp/collector-config.yaml:/etc/otelcol/config.yaml" \
     otel/opentelemetry-collector-contrib:latest --config /etc/otelcol/config.yaml
   ```
2. Point the send test at the real Collector (`:4318`):
   ```sh
   OTLP_PORT=4318 OTLP_NO_MOCK=1 sh tests/runtime/run_otlp_send.sh
   ```
3. If `spnl_method_calls_total` and friends show up in the Collector's debug
   exporter log, it worked.

## What this transport check does and does not cover

- What it sends is a **fixed sample** ExportMetricsServiceRequest, not live
  data. Carrying the real `--instrument` metrics over OTLP is a separate path.
- It exercises HTTP+protobuf only. gRPC (`:4317`) and TLS have their own
  scripts in `tests/runtime/` (`run_otlp_grpc.sh`, `run_otlp_tls.sh`).
